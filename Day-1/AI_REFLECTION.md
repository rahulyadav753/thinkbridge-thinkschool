I used Claude Code to refactor `OrderService` with a Strategy Pattern in this repository. The refactor moved business rule branches out of the service and into separate concrete rule classes like `OrderStatusRule`, `BulkDiscountRule`, `BlackFridayDiscountRule`, `WelcomeDiscountRule`, and others. Those rule classes were then registered with DI in `Program.cs` and executed through `IEnumerable<IOrderRule>`.

The first test run exposed a regression: a valid order expected `Status = "Review"`, but the returned status was empty. That bug was not in the rule itself; it was in the test setup. I discovered that the failing test instantiated `OrderService` with an empty `List<IOrderRule>()`, so `OrderStatusRule` never executed. I caught this by running `dotnet test`, reading the failure, and comparing the old and new service behavior.

I corrected the test setup by injecting `OrderStatusRule` into the constructor while keeping the original `Review` behavior unchanged. After that, I used Copilot to generate additional validation tests for negative quantity, zero quantity, and valid positive quantity. I reviewed those generated tests against the existing `OrderServiceTests` style and test patterns before accepting them.

What Claude got right was the overall refactor direction and the Strategy Pattern split: the service became an orchestrator and the rules became isolated classes. I would have caught the regression by rerunning tests and checking the diff around `OrderService` and `OrderServiceTests`; that is exactly where the bug surfaced. Copilot saved me time wiring up tests and staying consistent with existing xUnit conventions. Copilot was subtly risky when it suggested a test setup with no actual rules injected, because that could mask intended behavior in the service. At 2 AM IST in production, I would reach for the test suite first, because this project already had a failing regression and the unit tests pinpointed the issue quickly.
